# 调用 WorkBuddy

把用户描述的任务交给 WorkBuddy 执行，由当前主会话独立审查实际结果。主模型沿用当前选择；WorkBuddy 是执行平台，不把它伪装成可由通用子智能体工具选出的模型。

## 连接与派发

优先使用当前环境可用的 WorkBuddy 专用接口。没有发现专用接口时，用平台提供的界面操作能力驱动桌面应用。派发前核实目标系统上的桌面应用标识与当前可用的连接方式，不假定接口或路径存在，也不复用其他环境或历史会话的结论。

用户说“那个会话”“继续”时，先确认上下文指的是 WorkBuddy 会话，再在上下文中找到该会话并核对标题与内容，确认是同一任务再继续；新任务才创建新会话。读取当前界面的模型选择、工作空间与输入状态，不沿用旧索引或历史配置。用户要求的模型或推理强度无法设置时，只说明实际可观察状态。

## 派发契约

按共享框架规划任务。框架来源使用当前任务中已核实的本地框架 `AGENTS.md` 副本，或固定版本的规则 URL：
`https://github.com/1791986214/agent-framework/blob/main/AGENTS.md`。
派发前先核实本地副本可用或远端 URL 可读，并记录实际提交 SHA，在本任务中固定该版本；同时读取目标项目适用的 `AGENTS.md` 或同类约定。规则源保持只读。

每次只派发一个具体步骤。派发内容至少提供：规则来源、唯一任务文档的绝对路径、步骤编号、允许修改范围、验收条件与必需验证。任务文档含多个同形勾选行时，若所用的文件编辑工具要求匹配唯一，用步骤标题等上下文消歧。

写入权顺序交接：执行者只写本步的执行记录与完成项，审查与验收项由主会话独占。需要收窄写入范围时把范围写死在派发内容里——能访问某个文件不等于获准修改它，执行者不越界写入。

对简单的交接测试，可以约定一个固定回执串，便于按字面确认会话确实完成；但回执不能代替交付物与行为验收，真实任务也不必强制要求回执。

## 界面操作

项目文件可由获准的直接文件工具读取时，用文件路径和当前差异做代码审查；WorkBuddy 界面用于会话交接及必需的真实界面验收。优先读取与当前动作相关的界面状态，必要时再取完整状态或截图；不因省额度省略能证明结果的界面检查。

遵守界面操作的新鲜状态要求：发送前确认输入框中的全文与发送按钮状态，发送后确认会话中确实出现了该请求。状态不明时先检查，不重复派发同一步。若操作界面显示已输入文本却没有触发应用内部的输入状态，重新聚焦或重新渲染输入框后再检查。

输入可能异步更新；全文尚未稳定时先等待界面更新再判断是否失败。重试前核对已有草稿，避免反复追加同一请求。

先尝试支持 Unicode 的粘贴；当前接口无法正确输入中文时，可改用完整的英文派发指令，任务语义、路径与回执保持一致。

## 验收与用量

等待完成后读回会话结果和共享任务文档，核对实际产物及改动是否落在允许范围内。只看到成功回复不足以验收；执行者自身的回填记录是证据之一，但不是唯一依据。文件访问受阻或必需验证未完成时保持未验收状态，并写明已经核实和尝试过的事实。

执行者完成后，主会话独立检查改动与证据，填写审查并勾选验收项。涉及代码时执行步骤合同要求的验证；纯文档交接不追加无关的构建或数据库检查。

用量采用应用实际显示的数据并标明来源；文本里的估算不能冒充账单。单次调用成功不保证以后具有相同的成本、接口能力或权限。

## 技能维护

用户授权优化本技能时，把候选文件放在单独的可写路径，只授权 WorkBuddy 修改该候选和当前步骤的执行记录，主会话审查后再安装。普通 WorkBuddy 任务不自动修改技能、共享规则或应用设置。
