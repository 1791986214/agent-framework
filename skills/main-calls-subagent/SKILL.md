# 主智能体调用子智能体

当用户说“`<主智能体>` 调用 `<子智能体>`：`<任务>`”或含义相同的话时，按下面的流程把指定任务交给主智能体协调。无需要求用户重复填写表单。

用户指定 WorkBuddy 平台时，读取 [workbuddy-handoff](../workbuddy-handoff/SKILL.md) 完成会话连接与交接，再按本框架串行验收。

## 规则入口

读取共享规则，并把本次实际读取的提交 SHA 固定在任务文档；若平台已安装固定提交的规则入口，沿用该版本。随后读取目标项目适用的 `AGENTS.md` 或同类约定：

`https://github.com/1791986214/agent-framework/blob/main/AGENTS.md`

该版本规定规划、只读边界、单步委派、执行记录、主智能体审查与交付要求。不要把任务清单写进规则仓库；进度文档放在当前获准写入的项目或任务文档工作区。

## 角色与配置

- 主智能体沿用用户当前选择的模型；不根据“Sol”之类角色名伪称切换。
- 用户明确指定了执行模型或推理强度时，使用平台实际支持的子智能体配置。工具不能指定时，简短说明实际限制。
- 名称可以是角色称呼，也可以是模型名。仅将明确的模型配置传给委派工具；不要猜测映射关系。
- 本流程要求串行执行：一次只派发一个具体步骤。子智能体只负责该步骤，不提前做后续步骤或再次委派。
- 省额度不改变用户指定的模型或推理强度，也不减少必要的代码检查、测试和主智能体审查。未指定强度时按任务难度选择，不假定低强度总能完成。

## 执行

1. 从触发句和后续文字提取任务目标、范围、验收约束、执行者与配置。把用户原始任务保留在进度文档中。
2. 核对当前工作区、代码和 Git 状态、已有改动、前置步骤、验证环境及项目规则。历史行号和测试结果不是当前证据。
3. 在获准写入的工作区创建或续写唯一的方案与进度文档；用户已有清单、编号和依赖时先核实并遵守，其他步骤由主智能体规划。每步写清前置条件、允许修改范围、交付物、验收条件和必要命令。
4. 每次派发一个已就绪步骤。Codex 支持时用不继承旧聊天历史的子智能体调用，并传入自足的步骤合同、规则版本、项目约定、前置证据、相关路径和验证要求；子智能体重新核对当前代码。其实施该步所需代码、测试和合同文档，核实并记录实际命令与结果、修改文件、API/迁移变化、验证边界和遗留问题，然后只勾选自己的完成项。
5. 主智能体独立检查差异、业务不变量和实际验证证据。未通过时让当前步骤返工，不开始下一步；通过后主智能体记录审查并勾选验收项，才继续派发。
6. 每步结束向用户简报步骤、完成内容、关键决定、文件、迁移/API、实际验证、验证边界及遗留问题。全部规划步骤验收后给出总交付。

工具调用先读相关文件和差异，保留完整测试日志供追查，只向模型返回必要摘要与失败片段。真实界面行为需要验收时仍须实际操作；避免与代码检查无关的重复全屏状态或截图。长会话可在步骤边界用任务文档交接，不能丢失未解决合同或验收事实。

## 触发示例

`Sol 调用 Luna：按仓库的迁移清单核实现状，规划并完成所有未验收步骤。`

主智能体须把冒号后的请求作为本次任务来规划与执行，而不是只解释框架或仅创建空清单。若目标项目或必要权限确实无法从上下文确认，再报告具体阻塞事实。
