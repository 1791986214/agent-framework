# 多平台智能体协作框架

这是供不同智能体平台读取的纯 Markdown 框架。主智能体写方案和审查，执行智能体实施步骤并回填进度。模型由用户选择，步骤数量由主智能体规划。

入口是 `AGENTS.md`，任务模板是 `templates/TASK.md`。普通任务只需加载规则与当前任务文档；本说明用于配置和部署。

## 放置方式

推荐一个独立的 Git 规则仓库，加一个独立的任务文档工作区：

```text
agent-framework/                 # 各平台只读，固定到一个发布提交
  AGENTS.md                      # 唯一规则入口
  README.md                      # 部署与使用说明
  templates/TASK.md              # 只读模板

task-documents/                  # 获准写入的任务文档目录
  <任务名>.md                    # 方案、执行勾选、审查及交接记录

target-project/                 # 需要代码执行时另行授权
  <业务代码、测试、合同文档>
```

规则仓库适合放在 GitHub 或其他 Git 服务。每个平台读取同一发布版本或提交 SHA，避免读取随时变化的默认分支。可使用本地只读副本，或读取固定提交的文件 URL；执行智能体需要真实文件写能力，才能回填任务文档。

若通用规则可以公开，用户可选择公开规则仓库，让具备网络读取能力的平台读取固定版本，省去逐个平台配置私有仓库凭据。任务方案和业务数据继续放在独立的获准工作区，不随规则公开。规则需要保密时使用私有仓库并为各平台配置读取权限。GitHub 的公开仓库可供互联网用户读取。[GitHub 仓库可见性说明](https://docs.github.com/en/repositories/creating-and-managing-repositories/about-repositories)

Git 远程副本不是共享文件系统。多平台可以同时读规则，同一任务文档只允许一个当前写入者。最省请求的使用方式是在一个获准工作区内串行运行主、子智能体，本地写文档，交付时批量同步。跨机器交接时先同步最新任务文档和目标项目，再交出写入权；无需额外搭建调度服务。

## 规则防改的实际部署

按以下方式部署：

1. 用户维护规则仓库并发布固定版本；执行平台账号只给仓库读取权限，不持有规则仓库管理或写入凭据。
2. 将该固定版本放在执行沙箱的可读、不可写路径，或只读挂载。任务文档目录另设为可写，代码项目按任务授予范围。
3. 远程规则分支可锁定为只读，或要求用户审核规则更新，并收紧绕过权限。发布与更新由用户管理。
4. 开始任务、恢复或跨平台交接时核实所用版本。任务文档不能覆盖框架规则。

AGENTS.md 是行为规则，不是文件系统权限机制。普通本地文件的“只读”标记，如果执行进程仍拥有所有者权限和无限制命令能力，不能提供可靠隔离。远程分支保护也不能阻止本地文件被修改。因此必须由运行平台或系统实施写入限制，不能把文字约定当作已启用的保护。[GitHub 分支保护说明](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

本地交付只是仓库初稿，不表示远程分支保护、只读挂载或平台沙箱已配置。

## 跨平台入口

各平台的自动指令发现机制不同。支持 AGENTS.md 的平台按其发现规则配置；其他平台可用一条明确的启动指令让主智能体读取入口，避免维护多套规则副本。Codex 会按目录规则发现 AGENTS.md；放在无关目录的文件仍需要明确提供路径。[官方 AGENTS.md 说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

一句话启动，通常只替换目标：

> 读取 https://github.com/1791986214/agent-framework 的 AGENTS.md，你规划并审查、子智能体执行，完成：`<我的目标>`。

需要指定执行者时，在同一句里加“执行者用 `<模型>`，推理强度 `<强度>`”。主智能体沿用平台当前选择，其他配置、文档路径和步骤由主智能体根据现有工作区落实。模板是可选项，入口规则本身已包含最低必需的文档结构。

开始前，用户只需提供目标及平台无法自行确定的路径。若工作区和任务文档路径已可推断，主智能体按规则自行落实，不反复要求用户填写表单。

## 尽量少用额度与调用

建议先用平台已有的原生子智能体功能和本地文档，不搭建额外应用、MCP 服务或独立调度系统。

- 主智能体一次规划；按完整可验收结果合并步骤，简单任务可只有一步，不固定七步。
- 每步一次委派包含实施、必要测试、合同文档及回填；主智能体自己审查，不再启动审查或记录智能体。
- 只传本步必要上下文。规则版本未变时，同一会话不反复全文加载；新执行者仍需获得规则。避免复制完整聊天和大量旧日志。
- 使用完成通知或一次有界等待，不高频查进度。小工具动作和测试命令不要拆成独立模型任务。
- 必需验证保留；无新改动或新风险时不重复已通过的检查。
- 本地勾选文档，交接或交付时集中同步 Git，避免每次勾选通过 GitHub API 单独写文件。

如果任务被规划为 N 个必要步骤且没有返工，目标是 N 次步骤委派，由当前主智能体完成规划和 N 次审查。这里统计的是逻辑委派；每个智能体执行工具、继续推理都可能产生多次底层模型请求，不能承诺总请求为 N+1，也不能按委派次数推算账号额度。

默认采用每步一个边界清楚的子任务。平台若支持复用执行者，可以串行复用同一个执行会话，但每次必须明确新步骤合同；复用不保证更省额度，累积上下文可能抵消启动开销。

## 当前交付与远程发布

框架发布到 [1791986214/agent-framework](https://github.com/1791986214/agent-framework)，默认私有。具备该仓库读取权限的平台可通过已连接的 GitHub 账号或获准的本地副本读取入口；未登录的网页读取无法访问私有内容，不能声称已加载规则。

发布后将仓库归档，作为远程只读规则版本；任务进度写到独立文档工作区。归档可由仓库所有者主动取消，以维护并发布新规则。首次加载时记录实际提交 SHA，任务执行期间固定该版本。各平台的本地文件写入限制仍由该平台设置，仓库归档不能替代本地沙箱权限。
